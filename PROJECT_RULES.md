# Правила розробки — Mini GTD

Ці правила діють для всіх наступних задач у проєкті. Якщо задача
суперечить правилу — правило має пріоритет, і про конфлікт варто
повідомити перед тим, як щось змінювати.

1. **Мова інтерфейсу — українська.**
   Весь текст, який бачить користувач (написи, кнопки, заголовки,
   повідомлення про помилки, плейсхолдери), — українською.

2. **Не додавати зайвих файлів чи бібліотек без потреби.**
   Перш ніж підключати нову залежність або створювати новий файл —
   переконатися, що без цього справді не обійтись. Мінімальний
   набір інструментів для поточного кроку, не «про запас».

3. **Кожен компонент — в окремому файлі.**
   Без «богоподібних» файлів на кілька компонентів. Один файл —
   один компонент, названий за його призначенням.

4. **Кольори — лише через CSS-змінні (дизайн-токени).**
   Ніяких хардкоджених кольорів у компонентах (наприклад,
   `text-white`, `bg-gray-900`, `#0c0d0f` напряму в розмітці чи
   стилях компонента). Усі кольори визначаються один раз як
   дизайн-токени (CSS custom properties) і використовуються через
   `var(--...)`.

5. **Не додавати фічі, яких нема в плані.**
   Реалізується те, що описано в поточній задачі чи в
   [docs/PRD.md](docs/PRD.md). Ідеї «до речі, було б непогано ще…» —
   не втілювати одразу, а озвучити окремо.

6. **Бізнес-логіка не живе в UI-компонентах.**
   Компоненти відповідають за відображення й взаємодію з
   користувачем. Робота з даними, правила GTD-списків, збереження
   стану тощо — окремо від UI-шару (наприклад, у окремих модулях
   логіки/стору), а не всередині розмітки компонента.

7. **Обмеження середовища розробки (стосується AI-асистента).**
   - Немає збірника, немає `npm install`/`node_modules` — лише
     нативні ES-модулі й один CDN-імпорт (`@supabase/supabase-js`
     з esm.sh). Нову залежність не додавати без крайньої потреби
     (узгоджується з правилом №2).
   - AI-асистент **не пушить у git** (`git push`) і **не виконує
     SQL** проти Supabase (нові міграції в `supabase/migrations/`)
     — обидва рази це робить сам розробник вручну (SQL — у Supabase
     SQL Editor). AI-асистент **може** деплоїти Edge Functions
     (`supabase functions deploy ...`) — це не потребує доступу до
     секретів і не чіпає базу напряму.
   - AI-асистент **ніколи не бачить і не вводить самі значення
     секретів** (bot token, service_role key, API-ключі тощо) —
     лише називає, який секрет задати (`supabase secrets set
     ИМЯ=...`), значення підставляє сам розробник.
   - AI-асистент **не імітує й не проходить реальний вхід через
     Google** (OAuth) — це завжди робить сам користувач.
   - Кожна архітектурна зміна одразу відображається в
     [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) в тому ж кроці, не
     «пізніше»; те саме для [docs/PRD.md](docs/PRD.md), якщо
     змінюється сам продукт/фічі.
